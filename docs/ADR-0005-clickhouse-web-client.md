## Context

Issue #585 (Phase 7 of the #593 refactor umbrella) asked whether the official
`@clickhouse/client-web` package could replace the hand-rolled generic HTTP
transport in `src/net/ch-client.ts` — request construction, authentication,
result streaming, raw export bytes, cancellation, and the query-execution
retry policy `src/application/query-execution-service.ts` depends on. This
Phase 0 spike built a reusable, test-owned parity/precision harness under
`tests/spike/clickhouse-client/` comparing the real current production
functions (`runQuery`, `exportQuery`, `queryJson`, `authedFetch`, `killQuery`,
`killQueryWithLease`, `applyStreamLine`, `createQueryExecutionService`)
against an official-client spike adapter, ran the required
server/browser/build matrix, and reconciles this ADR from the recorded
evidence. Per the plan, the package stayed a spike-only `devDependency`
throughout: the normal production graph never imported it, and only a
spike-only candidate entry (`tests/spike/clickhouse-client/candidate-entry.ts`)
bundled it for measurement.

## Decision: Rejected

**`@clickhouse/client-web` is rejected for production adoption at this time.**
Three of ten hard gates fail, each with solid, independently-verified
evidence:

1. **Supported-server matrix fails.** Both proposed-oldest rows (ClickHouse
   24.8.14.39 OSS and 24.8.14.10547.altinitystable) fail. Root cause:
   `JSONStringsEachRowWithProgress`/`JSONEachRowWithProgress` never emit a
   `{"meta":[...]}` column-header line on ClickHouse 24.8 — that capability
   was added by ClickHouse GitHub PR #74181 ("JSONEachRowWithProgress format
   will include meta, totals, and extremes"), merged 2025-01-06, postdating
   24.8. `src/core/stream.ts`'s `applyStreamLine()` has no meta-less
   fallback, so every row silently maps to an empty/null value. **This
   affects the current production code equally** — it is a genuine,
   version-specific ClickHouse incompatibility, not an official-client
   defect: on both 24.8 rows, the live precision corpus shows
   `currentMatchesOfficial: true` (both adapters agree with each other) while
   `currentMatchesExpected: false` and `officialMatchesExpected: false` (both
   disagree with the independently-derived expected literal, identically).
   Both current-generation rows (26.6.2.160 OSS,
   26.3.16.10001.altinitystable) pass.
2. **Browser matrix fails.** 15 of 16 required row/origin/browser
   combinations pass (Chromium and WebKit, same-origin and cross-origin,
   across all four required server rows). The one failure —
   `current-altinity-stable / same-origin / webkit` — is an isolated flake
   attributed to this sandbox's simultaneous 4-container Docker contention
   during the live matrix run, not a genuine defect: a direct WebKit-only
   rerun passed 22/22 standalone, and the failure moved to a different
   specific test each rerun of the full 4-row matrix (see the `49b9955`
   commit message for the root-cause investigation). The mechanical gate
   still records `fail` because not every required row/browser combination
   passed in the recorded run — the plan's rule ("do not reinterpret an
   unknown, skipped, or partly observed hard gate as a pass") applies to
   flakes as much as to unknowns.
3. **Net production-code deletion is not positive.** Mechanically computed
   as **-103 estimated executable LOC** (240 eligible for deletion from
   `ch-client.ts`'s `delete-after-cutover` bucket, minus 248 for the
   official-adapter production-shaped core, minus 95 for the accepted narrow
   bridge/guard) — see `docs/evidence/585/deletion-estimate.md` for the full
   bucket breakdown and its own caveat that whole-function-granularity
   classification (required by this pass) likely understates the truly
   deletable portion of `authedFetch`, which mixes generic fetch mechanics
   with the narrow epoch guard.

All seven other gates pass: exact-value parity, progressive first-row parity,
mid-stream error parity, auth/epoch parity, raw/export bytes, single-file
build, and bundle delta (measured, not a pass/fail gate). See the decision
table below.

**Why a narrow bridge cannot resolve this.** The failing gates are not
symptoms a narrower `exec()`-based bridge (already the accepted design,
§16 below) can fix:

- The supported-server-matrix failure is a **server-side format gap** on
  ClickHouse 24.8 that exists independently of which HTTP client issues the
  request — the official client, the current custom transport, and any
  narrower bridge over either would all observe the same missing meta line.
  Narrowing the bridge changes nothing about what ClickHouse 24.8 sends.
- The browser-matrix failure is an **environmental flake**, not a code
  defect a bridge could fix.
- The deletion-estimate failure is a **structural** consequence of this
  package's guaranteed floor (24.8+) forcing a bridge (`progress-bridge.ts` +
  `guarded-fetch.ts`, 95 physical lines) that, combined with a
  production-shaped official adapter (248 lines) exceeding the 240
  deletable lines it would replace, produces negative net deletion. A
  smaller bridge would still need to reproduce authentication, epoch
  fencing, and the progress-format parsing that `authedFetch` +
  `applyStreamLine` already provide for free inside the current transport.

**The current custom transport (`src/net/ch-client.ts`) remains
authoritative.** No production behavior changed: the normal build
(`src/main.ts → dist/sql.html`) never imported the official client or the
spike harness, and this ADR does not propose changing that.

**Phase 1 remains useful independent of this decision.** Phase 1 (separating
application policy — retry safety, sessions, cancellation leases — from the
concrete generic-transport implementation in `src/net/ch-client.ts`) was
never contingent on adopting `@clickhouse/client-web`; `src/core/stream.ts`
and `src/application/query-execution-service.ts` are already isolated from
the transport choice (see `docs/evidence/585/deletion-estimate.md`'s "Other
named responsibilities" table), which is direct evidence that a Phase 1
transport-contract seam is a coherent, transport-agnostic refactor on its own
merits, not blocked by this Rejected result.

**Phases 2–4 do not proceed.** No production official-client implementation
(Phase 2), no production cutover (Phase 3), and no deletion of the generic
custom-transport code (Phase 4) may proceed from this ADR. Any future attempt
to adopt `@clickhouse/client-web` (or another official/generic client)
requires a new decision, informed by whichever of today's three failed gates
has changed — most plausibly the ClickHouse server-support floor, if a future
spike narrows its proposed minimum to a version this package's guaranteed
floor already reaches without gap.

derived and recorded live by `support-minimum.mjs`'s

1. The repository does not itself pin/promise a ClickHouse version anywhere
   in CI, Docker, deployment docs, demo config, README, or tests (checked

2. `@clickhouse/client-web`'s own README ("## Compatibility with ClickHouse",
   row "1.12.0+ | 24.8+") documents a guaranteed floor of **ClickHouse
   24.8+**.
3. The application-feature inventory (14 server-sensitive dependencies
   classified: required/optional/capability-gated, each with an earliest
   documented-support citation) found exactly one item that raises the floor
   above the client's documented 24.8+ guarantee: the
   `JSONStringsEachRowWithProgress`/`JSONEachRowWithProgress` meta-line
   requirement above, empirically confirmed absent on 24.8 and present by
   26.3/26.6 (PR #74181, merged 2025-01-06) — bounded, not pinned to an exact
   intermediate release, since no 25.x row was tested.
4. Intersecting the client's documented floor with that application
   requirement, and then testing the resulting candidates against the live
   hard gates (step 5 of the rule), the **earliest version that actually
   passed every required hard gate in this run is
   26.3.16.10001.altinitystable** — which exceeds the client's own documented
   floor, so it is the binding value per the `max(...)` formula.

**Proposed minimum: ClickHouse `26.3.16.10001.altinitystable`**, binding
source: earliest version that passed every required hard gate (live matrix).
Both 24.8-line rows are excluded by this derivation, which is exactly why the

## `JSONStringsEachRowWithProgress` disposition

Per plan §16's four allowed decisions, this spike selects **decision 2: a
narrow `exec()` bridge**.

- **Public type surface**: rejected. An uncast `query()` call with format
  literal `JSONStringsEachRowWithProgress` fails to compile against installed
  `1.23.1`'s public types — captured as a committed `@ts-expect-error` probe
  in `tests/spike/clickhouse-client/format-type-probe.ts`, with a positive
  `JSONEachRowWithProgress` control alongside it so a future type-surface
  widening makes `check:types` fail until the probe and this ADR are
  reconciled.
- **Raw `exec()` path**: viable. Executing SQL ending in
  `FORMAT JSONStringsEachRowWithProgress` through `exec()` exposes the raw
  byte stream incrementally, with a first row observable before completion,
  meta/row/progress/exception shapes intact, and exact string preservation —
  proven by the deterministic fault-server timing gate and the real-server
  corroboration on both current-generation rows.
- **Narrow progress bridge**: `progress-bridge.ts` (40 physical / 34
  transformed executable lines) incrementally decodes this exact
  newline-delimited UTF-8 JSON format, retains an incomplete line between
  chunks, parses complete records, emits existing `StreamLine` values, and
  surfaces in-band exceptions — it performs no result normalization, does
  not parse arbitrary formats, does not consume exports, and is not a second
  general client. `guarded-fetch.ts` (55 physical / 58 transformed
  executable lines) is the accompanying narrow credential-epoch guard
  (below).

## Precision

The exact-value parity gate (deterministic fault-server corpus: `ordinary-
query`, `table-streaming`, `empty-result`,
`url-parameters-arrays-and-large-integers`) **passes**. Separately, the live
39-case precision corpus (`docs/evidence/585/results.json.precision` —
`UInt64`/`UInt128`/`UInt256` maxima, `Int64`/`Int128`/`Int256` extremes,
`Decimal32`–`Decimal256`, `Date`/`Date32`, timezone-aware `DateTime`/
`DateTime64`, UUID/IPv4/IPv6, `Enum8`/`Enum16`, nullable, arrays, tuples,
maps, `LowCardinality`, JSON/Object, string edge cases including non-BMP
Unicode and NUL, and nested structures — each against an independently
derived expected literal) matches on **both current-generation server rows**
(26.6.2.160, 26.3.16.10001.altinitystable): every non-capability-gated case
has `currentMatchesExpected: true` and `officialMatchesExpected: true`.

On the two 24.8 rows, both adapters read back the *same* wrong (null/empty)
values for every precision case — `currentMatchesOfficial: true` on every
row even there — which is exactly the meta-line root cause attributed to the
supported-server-matrix gate above, not a precision-parity defect specific to
the official client. This corpus's row-level results are what feed
`precisionPass` into each matrix row's overall `passed`/`failed` status in
`compatibility-matrix.md`.

## Progressive timing

Deterministic fault-server fixture `delayed-headers-scheduled-rows`
(`docs/evidence/585/results.json.timing.deterministic`): current path first
row at 126 ms / completion at 1263 ms; official path first row at 125 ms /
completion at 1259 ms — the official path published its first normalized row
1 ms *ahead* of current, well inside the 100 ms tolerance, and did not buffer
through `.text()` or an equivalent whole-body read. Real-server timing
(`progressive-timing-real-server` scenario) corroborates this on both
current-generation rows; it fails on both 24.8 rows for the same meta-line
reason as the rest of that row's live suite, not a timing regression.

## Mid-stream errors

`mid-stream error parity` gate passes: `exception-after-headers-inband`,
`malformed-stream`, and `truncated-stream` all pass on the deterministic
fault-server corpus (`parity.test.ts`) — partial rows are preserved and the
stream never reports success after an in-band or late exception, tagged or
legacy-untagged. Real-server corroboration
(`mid-stream-progress-error-real-server`) passes on both current-generation
rows; it fails on both 24.8 rows for the same meta-line reason, not a
mid-stream-handling defect in the official path.

## Authentication and epoch

`auth/epoch parity` gate passes across `bearer-auth-exact-header`,
`jwt-as-basic-exact-composition`, `refresh-then-retry`,
`stale-before-request`, `stale-during-refresh`, and `stale-response`. The
deliberate epoch-flip race (request prepared, then the epoch is replaced
before the real fetch call) is caught by `guarded-fetch.ts`'s
injected-fetch-boundary check, not merely an adapter-side check before the
official API call — the plan's stronger, narrower guard option (§21), which
this spike proves sufficient without becoming a second generic request
implementation. Constructor count remains one across every alternating-
credential sequence (Basic user A / user B / Bearer fixture / invalid /
valid again): the official client is never mutated or reconstructed per
request or per refresh.

## Cancellation and retry

All three cancellation points (pre-aborted, abort awaiting headers, abort
after first row) preserve current partial-row and no-later-publication
semantics. Server cancellation (`server-cancellation-kill-query`) uses a
query ID allocated before execution, observed in `system.processes`, and a
`KILL QUERY` issued with the frozen request credential; it passes on both
current-generation rows and fails on both 24.8 rows for the shared meta-line
reason. Retry safety (`session-is-locked-live-retry`, plus the deterministic
`SESSION_IS_LOCKED`/connection-reset fixtures) shows exactly one safe retry
for reads and `SESSION_IS_LOCKED`, and no retry for ambiguous `INSERT`/DDL —
official outcomes feed the existing `QueryExecutionService` unchanged.

## Future production deletion estimate

Computed mechanically from `src/net/ch-client.ts`'s own top-level symbol
boundaries (`docs/evidence/585/deletion-estimate.md`), not a hand-typed
guess:

```text
current generic executable LOC eligible for deletion   =  240
- estimated official adapter executable LOC             =  248
- accepted narrow bridge/guard executable LOC            =   95
= estimated net executable LOC deletion                 = -103
```

Net deletion is **not positive** — an Accepted ADR requires positive net
deletion. Buckets not counted toward deletion each have exactly one final
owner (no permanent dual generic transport): `rewrite-narrow-adapter` (89
lines, credential-epoch fencing folding into the official adapter's own
request construction), `retain-temporary-bridge` (27 lines, `KILL QUERY` +
the frozen cancellation lease), `unrelated-product-operation` (626 lines,
schema/lineage/reference-data/doc-browsing SQL — never generic transport),
and `retain-as-sql-browser-policy` (`src/core/stream.ts`, 222 lines;
`src/application/query-execution-service.ts`, 291 lines — both already
isolated from `ch-client.ts` and unaffected by transport choice, direct
evidence for Phase 1's independent value, above).

The estimate's own documented caveat: `authedFetch` (89 physical lines) is
classified entirely as `rewrite-narrow-adapter` at whole-function
granularity because it interleaves generic fetch/response mechanics with the
narrow epoch guard; a finer sub-function split (out of scope for this
mechanical pass) would likely move some of those lines into
`delete-after-cutover`, making the net figure less negative or positive.
Reported as computed, not adjusted — a future re-evaluation could revisit
this specific caveat without needing to redo the rest of the spike.

## Consequences

- `@clickhouse/client-web` is **not** adopted. `src/net/ch-client.ts` is
  unchanged; production transport composition never changed during this
  spike and does not change as a result of this ADR.
- The dependency remains isolated to `tests/spike/clickhouse-client/` as a
  `devDependency`; nothing in this change requires removing it (it is a
  useful, reusable comparison harness per the invariant map), but it must
  never be imported from `src/`.
- Phase 1 (separating application policy from the concrete transport
  implementation) may proceed independently of this Rejected result, on its
  own merits — see "Decision" above.
- Phases 2–4 (production official-client implementation, cutover, and
  custom-transport deletion) do not proceed; #593's Phase 7 completes as
  Rejected, per the umbrella's own precommitted framing that a Rejected
  outcome still counts as complete.
- Re-open this decision only when at least one of the three failed gates has
  genuinely changed — most plausibly, a future ClickHouse-support-floor
  re-evaluation that lands `@clickhouse/client-web`'s guaranteed minimum on a
  version line where the meta-line gap and any newer server requirement no
  longer separate; or a smaller sub-function deletion-estimate split that
  turns the -103 LOC figure positive.

## Alternatives considered

- **Accept with a narrow `exec()` bridge, raising the supported minimum to
  26.3.16.10001.altinitystable.** Rejected: this still leaves net deletion
  negative (a structural, not incidental, result — see "Why a narrow bridge
  cannot resolve this" above) and does not remove the isolated browser-matrix
  flake as a source of "inconclusive-vs-fail" ambiguity for a future rerun.
- **Lower the proposed minimum to the client's raw documented floor (24.8+)
  without the application-inventory correction.** Rejected: this was the
  spike's own first-pass error (corrected in commit `49b9955`) — it would
  have silently classified a genuine version-specific incompatibility as
  "long-standing, predates every evaluated row," turning vendor-documented
  policy into an incorrect SQL Browser support claim (plan §40's "Proposed
  minimum may become accidental product policy" objection, realized and then
  caught).
- **Treat the WebKit flake as a browser-matrix pass on the grounds that
  22/22 passed standalone.** Rejected: the plan's rule that an unknown,
  skipped, or partly-observed hard gate is a failure for ADR purposes applies
  here; reinterpreting a recorded `failed` row as a pass would violate the
  evidence validator's own mechanical decision algorithm (plan §35 sabotage
  check 21, "force Accepted with a failed gate").

## Phase 1–4 boundaries

Per the approved plan (§4 "Explicitly deferred acceptance criteria"), none of
the following were attempted in this Phase 0 spike and none proceed as a
result of a Rejected ADR:

- Phase 1 — production `src/net/` transport contract; production import
  boundaries for the official client; shared contract tests for production
  transport implementations.
- Phase 2 — production official-client implementation.
- Phase 3 — production cutover and production-path behavior acceptance.
- Phase 4 — removal of obsolete custom generic transport code; actual
  post-cutover bundle/LOC comparison against this Phase 0 baseline.

Also out of scope, per the plan, regardless of this ADR's status: full
production browser E2E for login/Workbench/Dashboard/sign-out/export/
teardown; permanent live-ClickHouse CI integration; general supported-browser
documentation (tracked separately by #71); a permanent second transport
path.

## Limitations

- **ClickHouse Cloud was not evaluated** — no Cloud credentials were present
  in this environment. Per the plan, that conditional omission does not by
  itself fail this ADR; it is recorded as `not evaluated — no ClickHouse
  Cloud credentials in this environment` rather than silently skipped or
  reinterpreted as a pass.
- **The 25.x line was not tested** — the meta-line regression is bounded
  (absent on 24.8.14.x, present by 26.3/26.6) but the exact earliest passing
  minor release is not independently confirmed within that range.
- **Firefox is not a local acceptance signal** in this environment and is
  not claimed anywhere in this evidence, per the plan.
- **The deletion estimate is whole-function granularity** — see its own
  documented caveat above regarding `authedFetch`.
- **No startup parse/evaluation budget exists in this repository** to
  measure against (`results.json.startupParse`: "not applicable — repository
  has no existing startup parse/evaluation harness or budget"); none was
  invented solely for this spike, per the plan.
- **The isolated WebKit flake was not independently re-run inside this exact
  ADR-authoring session** — the root-cause analysis and 22/22 standalone
  reproduction are recorded in the `49b9955` commit message and this ADR
  relies on that prior, already-verified investigation rather than
  regenerating evidence, per this task's explicit scope boundary.
